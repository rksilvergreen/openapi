Operation Naming Algorithm (OpenAPI 3.0.0)
Step 1 — Use operationId if present

If operation.operationId exists and is non-empty:

Use it as the operation name after sanitization (target-language safe).

If sanitization results in an empty or invalid identifier, ignore and continue.

Rationale: operationId is intended to uniquely identify an operation across the API.

Step 2 — Derive from HTTP method + path template

If no usable operationId:

Take the HTTP method (get, post, put, delete, etc.).

Take the path template (e.g. /pets/{petId}/owners).

Split the path into segments by /.

For each segment:

Literal segment → use as-is.

Path parameter {param} → use param (no prefix).

Concatenate in order:

<method><Segment1><Segment2>...

Apply casing rules (e.g., lowerCamelCase or PascalCase).

Examples

GET /pets → getPets

GET /pets/{petId} → getPetsPetId

DELETE /pets/{petId}/owners/{ownerId} → deletePetsPetIdOwnersOwnerId

Step 3 — Hash-based fallback (last resort)

If Step 2 produces an empty or invalid name:

Compute a stable operation identity:

(documentUri, pathTemplate, httpMethod)

Generate:

op_<method>_<shortHash(identity)>

This guarantees determinism and uniqueness.
